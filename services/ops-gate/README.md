# ops-gate（署名済みの承認チケットで、許可した操作だけを実行する）

サーバー側で動く、小さなゲートです。**承認済みのチケットがあるときだけ**、ホストの設定で許可した操作を実行します。標準ライブラリだけで動きます。

LLMの提案を承認して実行するときも、管理画面（ダッシュボード）のボタンから実行するときも、**同じゲートを通します。** 安全装置と監査記録が1か所で済みます。

> 自分でSSH接続して操作するときは、このゲートを通す必要はありません。ゲートは、LLMと管理画面からの操作のための部品です。

## 守るもの

次のどれかが破られても、**それだけでは何も実行できない**ことを目標にしています。

| 破られたもの | 防ぐ仕組み |
| --- | --- |
| SSHの鍵が漏れた | 鍵は固定のコマンド（このゲート）しか呼べない。ゲートは署名つきチケットがなければ拒否する |
| 管理画面のセッションが乗っ取られた | 承認者のDiscord IDがホストの設定と一致しなければ拒否。チケットは短時間・1回限り |
| LLMが暴走した、または騙された | LLMはチケットを作れない。操作は許可リストの固定コマンドだけ |
| チケットが盗み見られた | 有効期限（既定15分）、1回限り、操作名と承認内容に紐づく |

## 動作

```text
承認サービス（管理画面）          ホスト
 承認者のDiscord認証の後に        ┌────────────────────────────────────┐
 チケットに署名                   │ ops_gate                           │
        │                         │  1. 署名を検証（HMAC-SHA256）       │
        └── "run <ticket> <sig>" ─▶│  2. 項目・型・期限・承認者を検証    │
                                  │  3. 操作が許可リストにあるか        │
                                  │  4. クールダウン・同時実行1件       │
                                  │  5. チケットを使用済みにする        │
                                  │  6. 事前チェック → 固定argvを実行   │
                                  │  7. 監査ログへ追記                  │
                                  └────────────────────────────────────┘
```

- **呼び出し側はコマンドを渡せません。** 渡せるのは、署名されたチケット（操作名を含む）だけです。実行するargvは、ホストの設定ファイルにだけあります。
- シェルは使いません（`shell=False`）。環境変数は `PATH` だけです。
- チケットは**実行の前に**使用済みにします。失敗した実行も再利用できません（もう一度承認が必要です）。
- 拒否されたときは、理由を監査ログに残し、呼び出し側には理由コードだけを返します。

## チケットの形式

承認サービス（`admin.ivrm.jp` のバックエンドなど）が作ります。

```json
{
  "v": 1,
  "op": "restart_herta",
  "proposal_id": "6f1c0e52-8f0b-4e8b-9d38-0c5b8a1d2e11",
  "proposal_hash": "<承認画面に表示した提案内容のsha256（hex 64桁）>",
  "approver_discord_id": "<承認者のDiscordユーザーID>",
  "issued_at": 1800000000,
  "expires_at": 1800000600,
  "nonce": "<16〜64文字のランダム文字列>"
}
```

- 署名: キーを昇順に並べ、空白なしで直列化した JSON（`sort_keys`、区切りは `,` と `:`、ASCII）のバイト列に対する `HMAC-SHA256(secret)`（hex）。
- 送信: `run <payloadのbase64url（パディングなし）> <署名のhex>`
- 項目は**これで全部**です。余計な項目があると拒否します（コマンドを紛れ込ませられないようにするため）。
- `proposal_hash` は、承認者が画面で見た内容（操作名・理由など）のハッシュにします。承認後に内容が差し替わっても、ハッシュが合わなくなります。
- 実装は `ops_gate/gate.py` の `sign_ticket` が参考になります（Node.jsなど他言語でも同じ手順で作れます）。

## 動詞

| 動詞 | 内容 |
| --- | --- |
| `run <ticket> <sig>` | 検証して、実行する |
| `check <ticket> <sig>` | 検証だけ。実行せず、チケットも消費しない（承認画面の事前確認用） |

終了コード: `0` 成功 / `10` 拒否 / `11` 実行に失敗・設定不備 / `12` クールダウン中または他の操作が実行中 / `64` 不正な要求

## 導入

1. ホストに配置する。

   ```text
   /opt/ivrm-ops-gate/ops_gate/      このディレクトリの ops_gate/（root所有、他者は書き込み不可）
   /opt/ivrm-ops-gate/run.sh         実行ビット付き
   /etc/ivrm-ops-gate/config.json    config.example.json をもとに作成
   /etc/ivrm-ops-gate/ticket-secret  32バイト以上のランダム値（chmod 600）
   ```

2. `config.json` に承認者のDiscordユーザーIDと、許可する操作の `argv` を書く。**`argv` が空の操作は無効**です。実際のコマンドは、サーバーの構成に合わせてあなたが決めます（このリポジトリには書いていません）。
3. SSHの専用鍵を作り、`authorized_keys` で**固定コマンドに縛る**。

   ```text
   restrict,command="/opt/ivrm-ops-gate/run.sh",from="<呼び出し元のIP>" ssh-ed25519 AAAA... ops-gate
   ```

   `restrict` で、ポート転送・エージェント転送・PTY・環境変数の持ち込みを止めます。あなた自身の管理用の鍵とは**別の鍵**にしてください。
4. 先に `check` で、チケットの検証だけを試す。

## 設定

| 項目 | 内容 |
| --- | --- |
| `approver_discord_ids` | 承認者のDiscordユーザーID（1人以上）。**このIDは設定ファイルにだけ置き、リポジトリには置きません** |
| `ticket_secret_file` | 署名の共有鍵。32バイト以上、グループ・他者から読めないこと（POSIXでは違反すると起動を拒否） |
| `state_dir` | 使用済みチケット、クールダウン、同時実行ロック |
| `audit_log` | 追記専用のJSON Lines |
| `max_ticket_age_seconds` | チケットの有効期間の上限（既定900） |
| `operations.<name>.argv` | 実行する固定コマンド。空なら無効 |
| `operations.<name>.timeout_seconds` | 超えると失敗扱い |
| `operations.<name>.cooldown_seconds` | 同じ操作の最短間隔 |
| `operations.<name>.precheck_argv` | 任意。終了コードが0以外なら拒否する事前チェック（例: オンライン人数が0か） |

## 限界

- 署名の共有鍵は、承認サービスとホストの両方にあります。承認サービスが侵害されると、チケットを偽造できます。ホスト側の許可リスト・クールダウン・短い期限が、その被害を限定します。
- 承認者が本当に本人かは、**承認サービス側のDiscord認証**に依存します。ゲートが確認できるのは、チケットに書かれたIDが設定と一致することだけです。
- クロックがずれると、期限の判定がずれます（30秒までは許容）。ホストの時刻同期（NTP）を有効にしてください。
- 実行したコマンドの中身の安全性は、ゲートでは保証できません。`argv` と、そのスクリプトの権限は、最小限にしてください。
