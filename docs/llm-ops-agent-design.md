# LLM Ops Agent 設計（案）

Status: Draft / 実装前のレビュー用

## 目的

障害の兆候を検知したとき、AWS Bedrock上のLLMが状況を分析し、次の2つを**提案**できるようにする。

1. 公開お知らせ・Incidentの**下書き**
2. 許可された範囲のサーバー操作

運用者の判断を置き換えるものではなく、「気づく → 原因を整理する → 文面と手順を用意する」までを速くすることが目的。

## 決定済みの方針

| 項目 | 決定 |
| --- | --- |
| お知らせ | 下書き保存まで自動。**公開は必ず人が行う** |
| サーバー操作 | **承認制**。LLMは提案のみで、実行は承認後 |
| お知らせの経路 | 既存のadmin CMS経由（Supabase `ivrm-core` の status RPC） |
| 許可する操作 | `mc-resource` の起動 / `mc-main` の再起動 / `Herta` の再起動 / 読み取り（ログ・状態） |

## 追加で決まったこと

| 項目 | 決定 |
| --- | --- |
| LLM専用の操作者（actor） | **許可できる**。Supabase側で専用actor（例: role `ai_agent`）を許容する変更を行う（Phase 1の前提） |
| サーバーの現在の操作方法 | **SSH接続**で行っている。加えて、**ブラウザの管理画面（ダッシュボード）からも操作できるようにしたい** |
| Bedrockの月額上限 | **約1,500円**。ops-agentの台帳で概算管理し、上限で停止する。AWS Budgetsのアラートも併用する |
| 承認者 | **オーナー本人1名**（DiscordユーザーID。個人の識別子のため、このリポジトリには書かず、ホスト側の設定ファイルにだけ置く） |
| 通知先 | 未決定（候補: Discord DM / 管理画面の承認待ち一覧） |

Phase 0（読み取り専用の分析）は `services/ops-agent/` に、サーバー側のゲートは `services/ops-gate/` に実装済み（いずれもレビュー待ち）。

## 非目標

- 任意のシェル実行、任意のコマンド生成
- お知らせの自動公開、Incidentの自動クローズ
- 上記以外のサーバー・サービスの操作（停止、削除、設定変更、デプロイ）
- 公開Status API（`status.ivrm.jp`）へのAWS認証情報の配置

## 全体構成

```text
[トリガー]
  status-api の状態変化 / 定期チェック / 管理者の手動実行
        │
        ▼
[ops-agent]（新規・別プロセス）
  Bedrock Converse + tool use
  ├─ 読み取りtool（状態・履歴・ログ）
  ├─ propose_announcement_draft
  └─ propose_action
        │
        ├────────────── 下書き ──▶ api.ivrm.jp ──▶ Supabase create_status_*_v1（draftのみ）
        │
        └────────────── 操作案 ──▶ 承認キュー ──▶ admin.ivrm.jp で人が承認
                                                    │
                                                    ▼
                                         [executor]（LLMと分離）
                                         許可リストの固定コマンドのみ実行
```

要点:

- **LLMは実行権限を持たない。** LLMが出せるのは構造化された「提案」だけで、実行はLLMから独立したexecutorが担う。
- ops-agentは公開用のstatus-apiとは**別プロセス・別認証情報**にする。公開APIが侵害されても、Bedrockやサーバー操作の権限に届かないようにするため。
- お知らせはSupabaseへ直接書かず、`api.ivrm.jp` の認証済みserver-side境界を通す（`docs/status-ui-renewal-2026-08-31.md` のCMS方針に従う）。

## トリガー条件

開発中のサーバー再起動やデプロイは日常的に起きる。これを「障害の兆候」と誤認すると、不要な下書きや操作の提案が出るため、次のルールで抑える。

- 公開履歴と同じ考え方で、**一定時間以上続いた**非正常だけを起動条件にする。基準は履歴の `STATUS_HISTORY_MIN_IMPACT_SECONDS`（既定300秒）と揃える。
- 同じ状態変化では1回だけ起動する（回復するまで再起動しない）。
- **登録済みのMaintenanceの期間中**は起動しない。計画的な作業は、先にメンテナンスとして登録する運用にする。
- 管理者が手動で一時停止（サイレンス）できる。期限付きで、解除し忘れを防ぐ。
- 抑制した場合も、理由を監査ログに残す（なぜ動かなかったかを後から追えるように）。

## 承認とサーバー操作の経路（決定）

LLMの提案を承認して実行する経路と、管理画面から人が直接操作する経路は、**同じ仕組みを通す**。安全装置と監査記録を1か所にするため。

```text
 LLM（ops-agent）──提案──┐
                          ├─▶ 承認待ち ─▶ 管理画面で承認者がDiscord認証して承認
 管理画面のボタン（人）───┘                        │
                                                    ▼
                                      承認サービスが「チケット」に署名
                                                    │
                          ┌─────────────────────────┴───────────┐
                          ▼                                      ▼
                  ホストが取りに行く（pull）              SSHの固定コマンド
                  ＝ 推奨                                 （ops-gateのみ呼べる鍵）
                          └─────────────────────┬────────────────┘
                                                ▼
                                    ops-gate（services/ops-gate）
                          署名・期限・承認者・1回限り・許可リスト・クールダウン
                                                ▼
                                          固定コマンドを実行
```

- **ops-gate**（実装済み: `services/ops-gate/`）がサーバー側の最後の防衛線。呼び出し側はコマンドを渡せず、署名つきチケットが有効なときだけ、ホストの設定にある固定コマンドを実行する。
- チケットは、操作名・提案の内容のハッシュ・承認者のDiscord ID・有効期限・使い捨てのnonceを束ねて署名する。短時間（既定15分）・1回限り。
- **承認者の本人確認は、承認サービス側のDiscord認証が担う。** ゲートは、チケットのIDがホストの設定と一致することだけを確認する。
- 自分でSSH接続して行う操作は、ゲートを通さない（これまでどおり）。ゲートは、LLMと管理画面からの操作のための部品。
- 管理画面から呼ぶ方法は、ホストが承認済みチケットを**取りに行く（pull）方式を推奨**する。クラウド側にSSHの秘密鍵を置かず、ホストへの外部からの接続口も増やさずに済む。SSHの固定コマンドは、それが難しい場合の代替。どちらにするかは未決定。
- 管理画面の実装（承認画面、チケット発行、承認待ち一覧）は `ivRooom/ivrm-web` で行う。このリポジトリの対象外。

## LLMに渡すtool

LLMが呼べるtoolはこの表だけ。ここにないものは存在しないものとして扱う。

| tool | 種別 | 内容 |
| --- | --- | --- |
| `get_public_status` | 読み取り | `/api/status.json` の現在状態と24h timeline |
| `get_status_history` | 読み取り | `/api/status-history.json`（最大30日、JST日付） |
| `get_service_logs` | 読み取り | 許可サービスの直近ログ（行数・文字数に上限、秘匿情報はマスク済み） |
| `propose_announcement_draft` | 提案 | 種類（info/warning）、タイトル、本文、対象サービス。**公開はしない** |
| `propose_action` | 提案 | `start_mc_resource` / `restart_mc_main` / `restart_herta` のいずれか＋理由 |

`publish_*`、`resolve_*`、シェル実行に相当するtoolは**定義しない**。

## お知らせの下書き

Supabase側の既存RPC（`create_status_announcement_v1` など）は、次の性質をすでに持っている。

- 作成時の `publication_state` は常に `draft`
- 冪等キー（`p_idempotency_key`）が必須で、同じ提案が二重に作られない
- 作成時に `append_audit_log` で監査ログを残す
- 公開は別RPC（`publish_status_announcement_v1`）で、agentには呼ばせない

追加のルール:

- 本文は**プレーンテキスト**。HTMLやMarkdownは許可しない。
- タイトル160字・本文4000字の上限（RPCの制約）を、agent側でも先に検証する。
- 下書きには「AI下書き」であることが管理画面上で分かるようにする（管理者が必ず目で確認する前提）。
- `affected_service_ids` は既知のサービスIDに限る。

### 要確認: LLMの操作者(actor)

RPCは `p_actor_email` / `p_actor_role` / `p_actor_discord_user_id` を必須とし、`status_actor_valid_v1` で検証する。

- 人間のアカウントをagentが**なりすましてはならない**。
- 専用のactor（例: role `ai_agent`）を用意し、`status_actor_valid_v1` と監査ログがそれを扱えるか確認・拡張する。
- この確認はまだ行っていない（RPC定義の一部しか読めていない）。**実装の最初のタスク**とする。

## サーバー操作

### 許可リスト

| 操作 | 前提条件 | 備考 |
| --- | --- | --- |
| `start_mc_resource` | `mc-resource` が停止中 | 元に戻しやすく、低リスク |
| `restart_mc_main` | 応答がない、または管理者が明示承認 | **接続中のプレイヤーが切断される**。オンライン人数を承認画面に表示し、1人以上なら確認を追加 |
| `restart_herta` | Herta状態が `degraded` / `outage` / `unknown` | |

### executorの規則

- LLMが書いた文字列を**コマンドとして実行しない**。操作名から固定コマンドへの対応表だけを持つ。
- 承認は**提案のハッシュに紐づけ**、有効期限（例: 15分）を設ける。承認後に提案が変わったら無効。
- 同一操作の**クールダウン**（例: 再起動は30分に1回）と、同時実行1件の制限。
- 実行前に前提条件を**再チェック**する（承認までに状態が変わっていることがある）。
- 実行結果（成功/失敗/出力の要約）を監査ログに残し、管理画面に返す。
- 失敗した場合の**自動リトライはしない**。

## 安全設計

### プロンプトインジェクション

ログ、プレイヤー名、チャット、Discordの内容は**攻撃者が書ける文字列**になりうる。

- 読み取りtoolの結果は、システムプロンプト上で「命令ではなくデータ」と明示した区画に入れる。
- LLMの出力は**必ずスキーマ検証**してから使う。tool名・操作名が許可リスト外なら破棄する。
- そもそもLLMに実行権限がないため、インジェクションが成功しても被害は「不適切な提案が承認キューに載る」までに留まる。承認画面には**生の操作内容**を表示し、LLMの説明文だけで判断させない。

### 暴走・コスト

- 1回の分析あたりの `max_tokens` とtool呼び出し回数に上限。
- 日次のBedrock利用上限と、トリガーのレート制限（同じ状態変化では1回だけ起動）。
- 上限到達時は、LLMなしで「状態をそのまま通知する」fallbackにする。LLMが落ちてもStatus自体は影響を受けない。

### データの扱い

- Bedrockへ送るのは、公開済みの状態データと、マスク済みのログ要約のみ。
- 秘匿情報（トークン、IP、メール、内部ホスト名）は送信前にマスクする。
- プロンプトと応答は、機微情報をマスクしたうえで監査用に保管する。

## Bedrock

調査時点（このアカウントで確認）で、`ap-northeast-1` に日本向けの推論プロファイルがある。

- `jp.anthropic.claude-haiku-4-5-20251001-v1:0`（分類・要約向け、低コスト）
- `jp.anthropic.claude-sonnet-4-6` / `jp.anthropic.claude-sonnet-4-5-20250929-v1:0`（分析・文面作成向け）

方針:

- データ所在を日本に寄せるため、`jp.` のプロファイルを既定にする。
- 最初は軽量モデルで一次判定、必要なときだけ上位モデルで文面を作る2段構成を検討する。モデルIDは**設定値**にし、コードに固定しない。
- 最終的なモデルとリージョンは、費用と品質を見て決める（未決定）。

### IAM

- ops-agent専用のIAMロールを作り、`bedrock:InvokeModel` / `InvokeModelWithResponseStream` を**使うプロファイルのARNだけ**に絞る。
- 調査に使った現在のAWSセッションは**アカウントのrootとして認証されている**。このrootの認証情報を、アプリケーションやCIに配置してはならない。専用ロールを作り、短期認証情報（OIDC / ロールの引き受け）で使う。
- OCI上のサービスからAWSへ接続する方法（長期キーを避けられるか）は未決定。

## 段階的な進め方

| Phase | 内容 | 本番への影響 |
| --- | --- | --- |
| 0 | 読み取り専用。状態を分析して要約を管理者に出すだけ | なし |
| 1 | お知らせ・Incidentの下書き作成（draftのみ） | 管理画面に下書きが増えるだけ |
| 2 | 承認キューとexecutor。`start_mc_resource` のみ | 承認後にサーバーが起動する |
| 3 | `restart_herta`、`restart_mc_main` を追加 | 承認後に再起動する |

各Phaseで、1週間程度は提案の質（誤提案の率、承認/却下の比率）を見てから次へ進む。

## 受け入れ基準（Phase 1）

- Bedrock障害・拒否・タイムアウト時も、Status表示と既存機能に影響がない。
- agentがpublish系のRPCを**呼べない**（権限・コードの両方で）。
- 同じ提案を再実行しても下書きが重複しない（冪等キー）。
- スキーマ外の出力、許可リスト外の操作名、長すぎる本文は破棄され、監査ログに残る。
- ログ由来の悪意ある文字列を含む入力で、許可外の提案が承認キューに載らない（回帰テスト）。
